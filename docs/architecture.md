# Куратор вкладок — архитектура

Статус: **черновик, прошёл первый круг адверсариальной проверки**. Документ
итеративно улучшается; ишью заводятся только из сошедшейся версии.

История ревью здесь не ведётся — только сведённый результат.

---

## 1. Проблема и цель

Вкладки размножаются и смешиваются: инфраструктурные дашборды (Proxmox, Portainer,
Grafana) живут вперемешку с временными вкладками, дубли одного дашборда копятся
десятками, «что уже открыто» не видно.

Цель — реконструкция механик Arc (Spaces / Air Traffic Control / Auto Archive /
Library / Command Bar) поверх нескольких изолированных инстансов Brave: тематические
браузеры-«корзины», правила «адрес → домашний инстанс», отложенная сортировка по
бездействию, стартпейдж со списком всего открытого.

Ключевой принцип: **не мешать в моменте, сортировать постфактум.**

```text
           │ wss:// (исходящее)          │
           ▼                             ▼
┌───────────────── curator-service (Docker) ─────────────────────────────┐
│ WSS  /ext      — канал расширений                                       │
│ HTTP /api/*    — состояние, правила, превью, архив, focus, quick links   │
│ HTTP /mcp      — MCP streamable HTTP                                     │
│ HTTP /healthz  — liveness; /metrics — Prometheus                         │
│ SQLite (WAL)                                                             │
│ Проход куратора раз в PASS_INTERVAL_MIN                                  │
└──────────────────────────────────────────────────────────────────────────┘
```

Адрес сервиса — конфигурация расширения (`serviceUrl`), а не константа дизайна.
Требование к нему одно: TLS-сертификат должен приниматься браузером без ручного
исключения, потому что расширение подключается из service worker'а, где ошибка
сертификата не даёт ни диалога, ни причины в JS — только `close` с кодом 1006.
Где публикуется сервис — вопрос деплоя, здесь не решается.

Стек — Python по каноническому гайду проекта: `src/` с pydantic-settings, вся
конфигурация из ENV, изменяемое состояние только в `data/`, тесты гейтят сборку.

**Донор** — `brave-window-mcp@f7f9c7c`: расширение берётся за основу (стр. 17),
Node-сервер не переиспользуется.

## 4. Модель данных

Канон схемы — этот раздел.

**Время.** Все метки в БД — epoch-миллисекунды **по часам сервиса**. Расширение
абсолютных клиентских временных меток не присылает вообще: вместо них — **возрасты**
(`ageMs`), которые сервис вычитает из своего `now`. Причина в §5.

`actions.kind ∈ {relocate, dedupe_close, singleton_close, window_merge, reset,
restore, cleanup}` — физическая операция. `actions.status ∈ {planned, opened, done,
failed, aborted, orphaned, deferred}` — жизненный цикл. `initiator` ортогонален
`kind`: MCP-инициированное переселение — `kind=relocate, initiator=mcp`.

`main_instance_id` живёт **только в ENV**, не в `settings`: две копии одного факта
без механической сверки — R3-нарушение.

### Слой доступа к БД

Из стр. 28 следуют обязательные требования:

- Все обращения к SQLite — вне event loop (`asyncio.to_thread` либо `aiosqlite`),
  соединение с `check_same_thread=False`.
- Один выделенный путь записи с явными `BEGIN IMMEDIATE` / `COMMIT` в `try/finally`.
  Неявные транзакции запрещены: отменённая корутина (разрыв WebSocket — это она)
  оставляет write-lock висеть до конца жизни соединения.
- Писатель обязан быть cancel-safe: отмена задачи соединения не должна происходить
  между записью и коммитом.
- `busy_timeout` задаётся явно, а не наследуется.
- WAL включается на старте.
- Бэкап — `VACUUM INTO`; он падает внутри открытой транзакции, поэтому корректность
  предыдущих пунктов — предусловие бэкапа. После каждой копии — `PRAGMA
  integrity_check` и sanity-запрос числа строк **до** ротации самой старой копии;
  успех экспортируется метрикой (§12).
- Миграции — раннер по `PRAGMA user_version`. **Каждый шаг — одна транзакция**,
  включающая и DDL, и присвоение `user_version` (в SQLite DDL транзакционен). Иначе
  шаг, упавший на середине, оставит версию старой, следующий старт переиграет его и
  упадёт на «duplicate column» уже навсегда — в crash-loop, ночью, без свидетелей.
  Перед первым шагом — `VACUUM INTO`-копия. Провал репортится метрикой, а не только
  падением процесса.

## 5. Время и критерий бездействия

### Эпоха сессии

`tab_id` осмыслен только внутри сессии браузера, а `instanceId` один и тот же между
запусками. Без эпохи команда может закрыть **не ту вкладку**, и архив запишет неправду.

- Расширение при старте генерирует uuid, хранит в `chrome.storage.session` (очищается
  при рестарте браузера, переживает смерть service worker), шлёт в `hello` и `resync`.
- Сервис проставляет `session_id` в каждую команду; расширение отвергает команду с
  чужим `session_id` кодом `stale_session`.
- Смена `session_id` ⇒ сервис удаляет все `tabs` инстанса и заводит заново с
  `opened_at = last_active_at = now`, `age_unknown=1`. Это реализует стр. 14 надёжно и
  независимо от того, переиспользует ли Chrome номера `tab_id`.

### Возрасты вместо меток

Расширение **не присылает абсолютных клиентских timestamp'ов**. В `resync` каждая
вкладка несёт `ageMs = Date.now() - tab.lastAccessed`; сервис пишет
`last_active_at = serverNow - ageMs`, но не больше `serverNow`.

Почему так: часы ноутбука могут уйти вперёд (севшая RTC, ручная правка, шаг NTP). При
работе с абсолютными метками и однократной калибровкой смещения в `hello` инстанс,
чьи часы обогнали серверные больше чем на `IDLE_MINUTES`, получает все вкладки
«бездействующими» — и ближайший проход выселяет его целиком. Монотонная дельта этим
не страдает и не требует выравнивания часов. Поле `clock_offset` в схеме отсутствует
намеренно.

### Часы вкладки

| Событие | `opened_at` | `last_active_at` |
|---|---|---|
| `tab_created` | `now` | `now` |
| `tab_activated {tabId, windowId}` | — | `now` — и **той же транзакцией** `now` для предыдущей активной вкладки этого окна |
| `window_focus_changed` (окно/приложение теряет фокус) | — | `now` для активной вкладки теряющего фокус окна |
| `tab_tick` | — | `now` |
| `tab_updated` со сменой url | — | `now` (навигация = активность) |
| `open_tab` ack (создана куратором) | `src_opened_at` из `actions` | `src_last_active_at` из `actions` |
| `resync`, та же эпоха, известная пара, тот же url | сохраняется | `max(сохранённое, serverNow - ageMs)` |
| `resync`, другая эпоха / неизвестная пара | `now`, `age_unknown=1` | `now` |

Обе колонки — `NOT NULL`. Предикат бездействия:
`serverNow - last_active_at >= IDLE_MINUTES * 60000`.

**Событие `tab_deactivated` не вводится**: в Chrome API его нет, а `onActivated` не
несёт `previousTabId` (это Firefox), поэтому расширению пришлось бы вести собственную
карту «окно → активная вкладка» и терять её при каждой смерти service worker. Вместо
этого штамп «ухода» ставит **сервис** внутри обработчика `tab_activated` — он и так
обязан там сбросить `active=0` у соседей по окну, и это единственное место, где оба
факта наблюдаемы одновременно.

**Тик активной вкладки.** Расширение по `chrome.alarms` раз в `TICK_MS` шлёт
`tab_tick {tabId, windowId}` — **только** для вкладки `active=true` окна, которое
сейчас в фокусе, и только пока приложение имеет фокус. Без тика «не трогал час»
означало бы «час не переключался на» (стр. 22): работаешь во вкладке два часа,
отводишь фокус — и через пять минут её увозит. Осознанное следствие: окно,
оставленное на переднем плане на ночь, не стареет.

**Почему не `lastAccessed`.** Стр. 22: он означает «стала активной» и не растёт, пока
во вкладке работают. Используется только как нижняя граница при ресинке.

### Активность и фокус

`active` в Chrome — свойство **окна**: последняя просмотренная вкладка тематического
браузера остаётся `active=1` навсегда. Поэтому «на экране прямо сейчас» — это
`tabs.active = 1 AND tabs.window_id = instances.focused_window_id`, а не один флаг
`active`. Хранить булев `focused` на инстанс недостаточно: при двух окнах он защищал
бы активные вкладки обоих.

`focused_window_id` — клиентский факт, который **переутверждается в каждом `resync`**;
`connected=0` тем же `UPDATE` обнуляет его в `NULL`. Иначе он залипает: ноутбук ушёл в
сон, событие потери фокуса не доставлено, и после возврата гард навсегда защищает
вкладку, которой на экране нет.

## 6. Протокол расширение ↔ сервис

Канон сообщений — этот раздел. Транспорт — WSS на `/ext`, JSON `{type, id?, …}`,
корреляция по `id`.

### Форма вкладки

`TabInfo = {tabId, windowId, url, title, favIconUrl, pinned, active, index, ageMs}`.
`ageMs` — см. §5. Тип окна приходит отдельным списком `windows` в `resync` и
событием `window_created`; вкладка, чьё окно сервису неизвестно, в проходе
пропускается.

### Установление связи

`hello {protocolVersion, token, instanceId, title, sessionId, allowExecuteJs}`
→ `hello_ack {ok, instanceId, connEpoch}`.

- `protocolVersion` — целое, сравнение точным равенством; несовпадение → отказ с
  записью `reject_reason='protocol'` и метрикой, а не тихая деградация.
- Неверный токен → `hello_ack {ok:false, error:{code:'auth'}}`, запись
  `reject_reason='auth'`, закрытие.
- Успех инкрементит `instances.conn_epoch`. **Все обработчики дисконнекта пишут
  условно**: `UPDATE instances SET connected=0, focused_window_id=NULL WHERE id=? AND
  conn_epoch=?`. Без этого добитый через полминуты полумёртвый старый сокет гасит
  живое новое соединение, и инстанс навсегда выпадает из курирования при исправной
  связи. События и ответы, пришедшие не с текущей эпохи, отбрасываются.
- Второй `hello` для занятого `instanceId` вытесняет старый сокет (закрытие +
  инкремент эпохи).
- После `hello_ack` сервис шлёт `resync_request {id}`.

### Готовность инстанса

`ready` — **вычисляемое условие**, а не хранимый флаг:

```
ready = connected = 1
    AND resync_at > pass_start
    AND session_id совпадает с последним hello
```

Хранимый флаг, который кто-то снимает, застревает: инстанс, потерявший `ready` из-за
одного таймаута, переставал бы получать `resync_request` (его шлют только `ready`) и
не мог бы восстановиться никогда. Поэтому `resync_request` рассылается **всем
`connected`**, а условие проверяется в момент использования.

### Ресинк

`resync {id, sessionId, snapshotSeq, focusedWindowId, tabs:[TabInfo], windows:[{id,type}]}`
— авторитетное полное состояние. Применение в одной транзакции: upsert всех
присланных вкладок, затем
`DELETE FROM tabs WHERE instance_id=? AND tab_id NOT IN (…) AND updated_at <= :snapshot_boundary`.

Условие по `updated_at` обязательно: снимок `chrome.tabs.query` собирается
асинхронно, поэтому строка, вставленная сервисом из ack на `open_tab` уже после
начала сборки, физически не могла в него попасть — без защиты «авторитетный» resync
её удалит, и следующая вкладка с тем же URL откроется вторым экземпляром.

По той же причине расширение не отправляет события, возникшие во время сборки
снимка, раньше самого снимка.

### События (расширение → сервис)

`tab_created {tab}`, `tab_updated {tabId, url?, title?, pinned?, favIconUrl?}`
(отсутствующее поле = не менялось), `tab_activated {tabId, windowId}`,
`tab_tick {tabId, windowId}`, `tab_removed {tabId, isWindowClosing}`,
`tab_attached {tabId, windowId, index}`, `window_created {windowId, type}`,
`window_removed {windowId}`, `window_focus_changed {windowId|null}`.

Событие про вкладку, которой нет в зеркале, **игнорируется** с инкрементом метрики и
дебаунсированным `resync_request` этому инстансу. Заводить строку-заглушку нельзя:
`opened_at` пришлось бы выставить в `now`, обнулив возраст вкладки.

### Heartbeat и переподключение

Сервис шлёт `ping` каждые `HEARTBEAT_MS`, помечая соединение `alive=false`; `pong`
возвращает `true`; два пропуска подряд → отмена задачи соединения и `close`
(Starlette не даёт принудительного разрыва, стр. 30 — механизм именно такой; писатель
БД обязан быть cancel-safe, см. §4). Параметры `ws_ping_interval` / `ws_ping_timeout`
uvicorn задаются явно, иначе действуют неявные 20/20 с.

**Переподключение ведёт `chrome.alarms`**, а не таймер внутри service worker'а:
обработчик алярма (период ≥ 30 с — минимум MV3) безусловно обеспечивает открытый
сокет, независимо от состояния в памяти. Таймер «не пришёл `ping` за
`2.5 × HEARTBEAT_MS`» — только оптимизация поверх. Причина: по стр. 23 таймер
простоя MV3 сбрасывает лишь трафик по сокету, поэтому при мёртвом сокете service
worker умирает через 30 с и внутренний таймер не сработает никогда — тематический
инстанс не вернётся после ночного передеплоя вообще.

Счётчик backoff сбрасывается **только после `hello_ack {ok:true}}`** — у донора он
сбрасывается в обработчике `open` (стр. 19), а при неверном токене сокет успевает
открыться, и отказ авторизации молотит раз в секунду вечно.

### Команды (сервис → расширение)

`command {id, sessionId, connEpoch, command, params}` → `response {id, ok, result|error}`,
где `error = {code, message}`. Коды: `stale_session`, `precondition_failed`,
`no_such_tab`, `no_window`, `js_disabled`, `busy_dragging`, `internal`.

| Команда | Параметры | Результат |
|---|---|---|
| `open_tab` | `{relocation_id, url, pinned, active:false}` | `{tabId, already?}` |
| `close_tab` | `{tabId, expect:{url, lastActiveAt}}` | `{ok}` / `precondition_failed` |
| `get_tab` | `{tabId}` | `{tab}` / `no_such_tab` |
| `focus_tab` | `{tabId}` | `{ok}` |
| `navigate_tab` | `{tabId, url}` | `{ok}` |
| `merge_windows` | `{}` | `{merged: n}` |
| `execute_js` | `{code, tabId?, world?}` | `{results}` / `js_disabled` |

**`expect` сверяет `url` и `lastActiveAt`, но НЕ `active`.** Гардом «не трогать то,
что на экране» служит §7.2, и дублировать его в предусловии нельзя: по §5 последняя
просмотренная вкладка несфокусированного инстанса имеет `active=1` вечно, поэтому
предусловие `active:false` отказывало бы каждый проход — ровно для той вкладки, ради
которой строится система. Сверка по `lastActiveAt` — это CAS по той самой величине,
из которой принималось решение, и она же закрывает все гонки «человек трогает вкладку,
пока идёт проход».

**`relocation_id` детерминирован и стабилен между проходами**:
`sha256(instance_from, session_id_src, tab_id, url, instance_to)`, он же — `UNIQUE` в
`actions`. Иначе идемпотентность не работает именно в том случае, ради которого
введена: потерянный ack даёт `failed`, следующий проход генерирует новый id, и в
цели появляется вторая копия — в `main`, где дедупа нет by design.

Расширение перед возвратом `already:true` **обязано подтвердить вкладку** через
`chrome.tabs.get` и пересоздать её, если она исчезла: иначе сервис получит
`{tabId, already:true}` на закрытую вкладку, вставит строку и закроет источник —
вкладка потеряна.

Карта `relocation_id → tabId` в `chrome.storage.session` чистится по
`chrome.tabs.onRemoved` и при терминальном статусе на стороне сервиса.

### Манифест расширения

- `permissions`: `tabs` (иначе `url`/`title`/`favIconUrl` отсутствуют, стр. 26, и
  правилам не с чем работать), `scripting`, `alarms`, `storage`.
- `host_permissions`: origin сервиса. `<all_urls>` — только ради `execute_js`.
- `content_security_policy.extension_pages` — дефолт (`script-src 'self'`).
- `chrome_url_overrides.newtab` → страница стартпейджа.
- `key` — фиксирует ID расширения независимо от пути (стр. 21).

### Внутренний интерфейс страница ↔ service worker

`runtime.sendMessage`: `get_identity` → `{instanceId, title}`;
`get_connection_state` → `{connected, lastSeenAt, rejectReason}`;
`enqueue_quicklink_op {op, url, title}`. Стартпейдж не хранит токен сам.

## 7. Проход куратора

Периодичность — `PASS_INTERVAL_MIN`. У прохода есть `pass_id`, он пишется во все
строки `actions` — это делает «откатить весь проход» одной операцией.

**Аренда с fencing.** `settings.pass_lease = {owner, epoch, until}`. Захват и
продление — одним CAS-запросом; продление каждые `LEASE_TTL_MS / 3`. **Каждая
запись прохода условна по `epoch`**: ноль изменённых строк ⇒ проход немедленно
прекращается. TTL без токена даёт только освобождение, но не взаимное исключение:
зомби-проход, переживший свой TTL, иначе продолжил бы слать команды параллельно с
новым — то есть механизм ломался бы ровно в том сценарии (rolling-редеплой), ради
которого введён.

**Реконсиляция — в начале каждого прохода**, а не только на старте процесса. Строки в
`planned`/`opened` разбираются по существу: `get_tab` по `target_tab_id`, и либо
переселение доводится до конца, либо закрывается осиротевшая копия (`kind=cleanup`).
Слепая пометка `aborted` запрещена — она переклеивает ярлык вместо компенсации и
понижает завершившееся переселение до фантома, а осиротевшая копия остаётся в `main`
навсегда (дедупа там нет).

Далее для каждой вкладки:

1. **Свежесть.** Проход начинается с `resync_request` каждому **`connected`**
   инстансу; в работу берётся инстанс, чей `resync_at > pass_start`. Не ответивший за
   `RESYNC_TIMEOUT_MS` из прохода исключается.
2. **Гарды.** Пропустить, если: url не http/https; `pinned=1`;
   `active=1 AND window_id = focused_window_id`; бездействие меньше `IDLE_MINUTES`;
   есть действующая запись в `exemptions`; есть действующая запись в `quarantine`.
3. **Куда.** Правило есть и инстанс ≠ домашний → домой; **это относится и к `main`**:
   `main` — источник для ruled-вкладок и не источник для unruled. Правила нет и
   инстанс тематический → в `main`. Правила нет и инстанс = `main` → не трогать.
4. **Цель не готова** → одна агрегированная строка `deferred` на проход (не строка на
   вкладку: 200 вкладок × проход раз в 5 минут = ~29 тысяч строк за ночь, и архив
   как страховка перестаёт быть читаемым).
5. **Дедуп и singleton — только с подтверждением от браузера.** Свежий `resync`
   источником подтверждения **не является**: он может быть старым на весь проход, а
   при гонке со снимком — ложно-свежим. Проверка — `get_tab` непосредственно перед
   закрытием источника; если для целевой вкладки успел прийти `tab_removed`,
   закрытие отменяется.
6. **Переселение.** `open_tab {relocation_id}` → ack → строка `tabs` для новой
   вкладки вставляется **синхронно из ack** в той же транзакции, что и обновление
   `actions`, причём `opened_at`/`last_active_at` **переносятся из источника**
   (`src_opened_at`, `src_last_active_at`) → `close_tab {tabId, expect:{url,
   lastActiveAt}}`.
   - `precondition_failed` → компенсация: закрыть свою копию в цели, источник не
     трогать, `status='aborted'` только при успешной компенсации; иначе `orphaned` с
     ретраем в следующем проходе.
   - Таймаут/`no_such_tab`/`stale_session` → та же компенсация, `status='failed'`.
     Источник не закрывается никогда.
7. **Изоляция.** Каждая вкладка — в своём `try/except`; аренда снимается в `finally`.
8. **Карантин.** Три подряд **неудачи** (`failed`/`aborted` при готовой цели) по
   `(instance_id, url)` → запись в `quarantine` с `until = now +
   QUARANTINE_TTL_MIN`. `deferred` неудачей **не считается**: иначе закрытый на обед
   `main` за три прохода отправил бы в вечный карантин все вкладки всех инстансов, и
   курирование встало бы после совершенно штатного события. Ключ по URL, а не по
   `tab_id`: последний испаряется при рестарте браузера. Карантин снимается по TTL,
   при смене `session_id` любой из сторон, при смене url вкладки и вручную.

**Сходимость.** Дублирующиеся одинаковые URL внутри одного не-`main` инстанса
схлопываются. Сравнение — точное по строке `tabs.url`: нормализация (снятие
фрагмента) закрывала бы реально разные страницы SPA, ради чего и введён `singleton`.
Выживает вкладка с бо́льшим `last_active_at`, но **строки с `age_unknown=1`
проигрывают наблюдаемым при прочих равных**, а перенос часов из источника (п. 6)
не даёт свежесозданной копии выигрывать у оригинала: иначе недельная рабочая вкладка
со скроллом и открытыми панелями систематически уничтожалась бы в пользу пустой
свежезагруженной.

**Ограничителя числа действий нет** (стр. 15). Защита от испорченного правила —
превью при сохранении (§8), `run_pass {dry_run:true}` и архив с откатом прохода.

`dry_run` берёт аренду, шлёт `resync_request`, `actions` не пишет, счётчики попыток и
карантина не трогает, возвращает план в ответе.

## 8. Правила

Канон семантики матчера — этот раздел, единственный. **Реализация каноническая —
серверная (Python)**; браузер матчер не дублирует.

- Правило: `pattern → instance_id` + флаги `singleton`, `canonical_url`, `note`.
- Схемы кроме http/https не матчатся никогда.
- Разбор: `urlsplit`, затем явная нормализация — `hostname` в нижний регистр, IDN →
  punycode (`idna`), снятие завершающей точки FQDN, IPv6-литерал приводится к форме
  без скобок. Отсутствующий порт = порт по умолчанию схемы (80 / 443).
- `pattern` = `<hostPattern>` или `<hostPattern>:<port>`; порт отсутствует → любой.
- `hostPattern` сравнивается с `hostname` целиком (anchored), `*` → `.*`, остальное
  экранируется. Частичного совпадения нет: `borneo.lc` не матчит ни `evil-borneo.lc`,
  ни `x.borneo.lc`.
- Специфичность: (а) явный порт специфичнее его отсутствия; (б) больше символов в
  `hostPattern` без учёта `*`; (в) меньший `rules.id`.
- **Валидация при сохранении**, а не исключение во время прохода: паттерн, который
  не разбирается (например, введённый как полный URL `https://borneo.lc/path`),
  отвергается с человекочитаемой ошибкой. Уже сохранённое правило, которое перестало
  компилироваться, помечается `invalid=1`, в матчинге не участвует, считается в
  метрике и подсвечивается в редакторе — но **никогда не роняет проход**.
- **Пустая таблица правил отключает ветку «unruled → main» целиком.** Пустая политика
  означает «ничего не делать», а не «переселить всё».

`singleton=1` — «приложение» (прокс, Portainer, Grafana): в домашнем инстансе
максимум одна вкладка на правило. Точный URL-дедуп таких не ловит: SPA-фрагменты
делают адреса формально разными.

**Превью — серверное** (`POST /api/rules/preview`), а не браузерное: иначе оно
считалось бы другой реализацией матчера и систематически врало бы на IDN и IPv6 — а
превью по стр. 15 единственная защита вместо снятого ограничителя. Превью возвращает
**раздельно** число переселений и число закрытий со списком примеров URL; необратима
именно вторая цифра. При `closures > 0` сохранение требует подтверждения.

`canonical_url` применяется **только** ручным действием `reset` (§10, §11); проход
содержимое вкладок не меняет.

**Нативно закреплённые вкладки (`pinned=1`) не переселяются и не закрываются.** Это
моё дизайн-решение, не решение владельца: он убрал пин как *механизм маршрутизации*
(стр. 5), здесь пин используется как сигнал «руками не трогать». Убирается одной
строкой в §7.2.

## 9. Окна

Инвариант «одно окно на инстанс» — цель использования (стр. 7), а не задача софта.
Автоматического слияния нет: оно косметическое, а его отказ («вытащил дашборд во
второе окно, чтобы смотреть два графика рядом, и через пять минут его схлопнуло — и
так каждые пять минут») — самая вероятная причина выключить систему целиком. Вместо
этого кнопка «слить окна» на стартпейдже и MCP-инструмент.

Следствие: инвариант не гарантирован, поэтому `open_tab` выбирает окно
детерминированно — обычное окно с наибольшим числом вкладок. Если обычных окон нет
(на macOS браузер живёт с нулём окон ежедневно) — `chrome.windows.create` с
`focused:false, state:'normal'`; фоновое окно не прерывает работу, а отказ уводил бы
инстанс в `deferred` и далее в карантин.

`merge_windows` восстанавливает `pinned` явно: перенос вкладки его сбрасывает. Отказ
`busy_dragging` (человек держит вкладку мышью) провалом не считается.

## 10. Стартпейдж и HTTP API

Newtab-страница расширения (стр. 25). Сборка — Vue 3 + Vite в папку расширения.

**Оффлайн-first (стр. 9).** Первая отрисовка не ждёт сети: свои вкладки —
`chrome.tabs.query`; чужие инстансы и quick links — кэш в `chrome.storage.local`
(ровно объект `StateResponse` плюс `cached_at`); затем фоновый `GET /api/state`
обновляет данные и кэш. Формулировка «синхронно» некорректна — в MV3 оба API
асинхронны; корректно: «первая отрисовка только из локальных источников».

Все ассеты локальны. В оффлайне свои вкладки и quick links полностью рабочие; чужие
группы помечены «кэш от &lt;время&gt;»; прыжок на чужую вкладку неактивен. Пустого newtab
не бывает, в том числе на свежем профиле без кэша.

**CSP-ловушка (стр. 29).** Только runtime-only импорт `vue`; `vue/dist/vue.esm-bundler.js`
или строковый `template:` тянут `new Function`, который блокируется `script-src
'self'`, и страница умирает молча. Защита — grep по `dist/` на `new Function|eval(`
в CI. Dev-сервер Vite для страницы расширения непригоден; цикл — пересборка.

**Статус-полоса различает четыре состояния инстанса**, а не два: никогда не видели /
видели N назад (закрыт) / подключён, но зеркало не свежее / отвергнут с причиной и
временем. Иначе отказ авторизации, несовпадение версии протокола, умершая от CSP
страница, блокировка LNA и «браузер просто закрыт» выглядят одинаково — серым
инстансом. Бейдж `chrome.action.setBadgeText` показывается внутри отказавшего
браузера, то есть там, куда владелец и не заходит; полагаться на него нельзя.

**Прыжок.** Своя вкладка — `chrome.tabs.update` + `chrome.windows.update`. Чужая —
`POST /api/focus`. Поднимет ли macOS чужое приложение — не доказано (стр. 33),
поэтому до результата спайка §14.1 UI показывает «активировано в &lt;инстанс&gt;» и подъёма
не обещает.

**Quick links.** Очередь оффлайн-операций живёт в `chrome.storage.local` (оффлайн
может длиться днями, `storage.session` умрёт с браузером), принадлежит service
worker'у, сливается `POST /api/quick_links/ops` с `Idempotency-Key`. Разрешение
конфликтов — last-write-wins по времени приёма на сервере; `position` пересчитывает
сервер (append в конец), явная операция `reorder` для перестановки.

### Эндпоинты

| Метод | Путь | Тело / ответ |
|---|---|---|
| GET | `/api/state` | `StateResponse` |
| POST | `/api/focus` | `{instance, tabId}` → `{ok}` |
| GET/POST/PUT/DELETE | `/api/rules[/:id]` | CRUD; POST/PUT требуют `confirm_impact` при `closures>0` |
| POST | `/api/rules/preview` | `{pattern, instance_id, singleton}` → `{relocations, closures, examples[]}` |
| POST | `/api/rules/:id/reset` | → `{ok}` (ручной `reset`, §8) |
| GET | `/api/actions` | `{items[], total}`; фильтры по `kind`, `pass_id` |
| POST | `/api/actions/:id/restore` | → `{ok}` |
| POST | `/api/passes/:pass_id/undo` | откат прохода целиком |
| POST | `/api/run_pass` | `{dry_run?}` → план или `{started}` |
| GET/POST/DELETE | `/api/exemptions` | «не трогать до …» |
| POST | `/api/quick_links/ops` | массив операций |
| POST | `/api/instances/:id/merge_windows` | → `{merged}` |

```
StateResponse = {
  server_now, last_pass_at, last_pass_ok, rules_total, rules_invalid,
  instances: [{id, title, connected, resync_at, last_seen_at,
               reject_reason, reject_at, focused_window_id}],
  tabs:      [{instance_id, tab_id, window_id, url, title, fav_icon_url,
               pinned, active, last_active_at, age_unknown}],
  quick_links: [{id, url, title, position}]
}
```

Свои вкладки клиент отфильтровывает сам (они уже есть из `chrome.tabs.query`).

**`restore`.** Открывает URL в `instance_from`, если тот готов, иначе отказ с явной
ошибкой (молчаливая подстановка `main` кладёт вкладку не туда). В одной транзакции с
открытием пишется `exemptions` с `until = now + RESTORE_EXEMPTION_MIN`, иначе
следующий проход выселит восстановленную вкладку снова — и так по кругу, пока она не
уйдёт в карантин, то есть «restore ломает вкладку». Перед открытием — дедуп по URL.
Пишется одна строка `actions(kind='restore', initiator='user')`, в исходной строке
проставляется `restored_at`.

## 11. MCP

`POST /mcp`, streamable HTTP (стр. 13). Auth — `Authorization: Bearer <MCP_TOKEN>`.

**Монтирование (стр. 27).** `mcp.run(transport="streamable-http")` поднимает
собственный uvicorn и забирает порт; `app.mount("/mcp", …)` даёт 307/404/500.
Рабочий паттерн: один раз вызвать `mcp.streamable_http_app()`, чтобы материализовать
session manager; войти в `mcp.session_manager.run()` в lifespan **хост-приложения**;
зарегистрировать точный `Route("/mcp", endpoint=StreamableHTTPASGIApp(
mcp.session_manager), methods=["GET","POST","DELETE"])` — именно `Route`, не `Mount`
(Mount добавляет 307 на `POST /mcp`, а httpx-клиенты MCP редиректы не следуют).
Версия SDK пиннится: `StreamableHTTPASGIApp` не в публичном `__all__`.

**Чтение и запись разделены.** Инструменты чтения — всегда: `list_instances`,
`list_tabs`, `get_rules`, `list_actions`, `run_pass {dry_run:true}`. Инструменты
записи (`upsert_rule`, `delete_rule`, `open_tab`, `close_tab`, `focus_tab`,
`relocate_tab`, `reset_singleton`, `merge_windows`, `execute_js`, `run_pass` без
`dry_run`) доступны только при `MCP_WRITE_ENABLED=true`.

`upsert_rule` подчиняется тому же правилу подтверждения, что и HTTP: возвращает
impact и требует эхо `confirm_impact`. Иначе из трёх заявленных защит (§7) на пути
MCP не работала бы ни одна: превью живёт в UI и не вызывается, `dry_run`
опционален, архив — постфактум.

## 12. Отказы, наблюдаемость, безопасность

### Наблюдаемость

- **`/metrics`**, Prometheus, Bearer по отдельному `METRICS_TOKEN` — read-only.
  Отдельный токен обязателен: у владельца scrape-креденшл лежит открытым текстом в
  git (стр. 32), и если это окажется `EXT_TOKEN` или `API_TOKEN`, в историю навсегда
  уедет ключ от правил, `run_pass`, `restore` и списка всех URL.
- Метрики: `curator_last_pass_ts`, `curator_last_pass_ok`,
  `curator_actions_last_pass{kind}`, `curator_instance_connected{id}`,
  `curator_instance_last_seen_ts{id}`, `curator_auth_rejections_total`,
  `curator_deferred_total{to_instance}`, `curator_quarantined_total`,
  `curator_rules_total`, `curator_rules_invalid`, `curator_backup_last_ok_ts`,
  `curator_backup_bytes`, `curator_migration_failed`.
- **Алерты — часть этого дизайна, а не «метрики есть».** В конфиге владельца ровно
  одно правило с `noDataState: Alerting`, и оно привязано к gitmost (стр. 31);
  правило, скопированное в домашнем стиле, при исчезновении данных уйдёт в `OK`,
  то есть замолчит ровно при аварии. Минимум: `up{job="curator"}` и
  `time() - curator_last_pass_ts > 3 * PASS_INTERVAL`, оба с `noDataState: Alerting`,
  плюс правило на `curator_last_pass_ok` и на возраст бэкапа > 36 ч.
  `curator_instance_connected` алертабельной не является — ноутбук спит каждую ночь.
- **`/healthz` — только liveness.** Ошибки курирования в него не складываются:
  оркестратор перестаёт направлять трафик в нездоровый контейнер, и «проход сломался»
  превратилось бы в «все расширения отвалились».

### Отказы

- Backoff сбрасывается только после успешного `hello_ack` (§6).
- `main_instance_id`, который ни разу не подключался → ветка стока выключена,
  метрика и баннер.
- `rules.instance_id` валидируется против `instances` при записи: опечатка в имени
  инстанса иначе даёт вечный невидимый `deferred`, а превью её не покажет — оно
  считает совпадения паттерна, а не существование цели.
- Ретеншн `actions` — `ACTIONS_RETENTION_DAYS`; окно восстановления документируется
  как заведомо меньшее. `js_audit` — свой, длинный ретеншн.
- Бэкап — ночной `VACUUM INTO` с `integrity_check` и метрикой успеха; путь копий
  монтируется отдельно от тома БД.

### Безопасность

- **`API_TOKEN` отдельно от `EXT_TOKEN`.** Один общий токен означал бы: утечка из
  одного одноразового тематического браузера (а он лежит открытым текстом в
  `chrome.storage.local` каждого профиля) даёт и весь `/api/*`, и право
  представиться любым `instanceId` по WS — включая `main`, чей `resync` делает
  `DELETE`.
- **CORS — только явные `chrome-extension://`-origin'ы**, никогда `*`. Заголовок
  `Authorization` вынуждает preflight, что дополнительно отсекает случайные страницы.
- Требование к развёртыванию: сервис не должен быть доступен из публичной сети.
- Все токены обязательны, пустой = отказ старта.
- `execute_js` — галочка в options каждого расширения, дефолт выкл, enforcement на
  краю (стр. 12). Инстанс сообщает состояние галочки в `hello`. Каждый вызов пишется
  в `js_audit` **до отправки** (чтобы отказы тоже попадали): полный код, `world`,
  `tabId` и URL на момент выполнения, исход. Усечённый код нереконструируем, а общий
  ретеншн с рутинными `dedupe_close` уничтожал бы единственный след выполнения
  произвольного кода вместе с шумом.

## 13. Инстансы

Инстанс — отдельный `.app`, запускающий системный Brave со своим `--user-data-dir`
(стр. 4). Генератор создаёт бандл с уникальным `CFBundleIdentifier`, иконкой и
лаунчером.

Расширение ставится флагом `--load-extension` (стр. 20). Оговорки: не сработает при
включённом Enhanced Safe Browsing и при политике `ExtensionInstallTypeBlocklist`.
Запасной путь — CDP `Extensions.loadUnpacked` (с M149 без спецфлагов).

**Риск:** иммунитет Brave держится на том, что проверка в апстриме сидит внутри
`#if BUILDFLAG(GOOGLE_CHROME_BRANDING)`. Если Chromium вынесет её наружу, Brave
унаследует запрет на ближайшем ребейзе без сигнала — поэтому запасной путь описан
заранее.

## 14. Открытые спайки

### 14.1. Кросс-инстансный фокус окна на macOS

Поднимает ли `chrome.windows.update(id, {focused:true})` в инстансе B приложение B
поверх A. Дизайн корректен при обоих исходах: при отрицательном UI не обещает
подъёма. Проверить для трёх состояний окна B: обычное, свёрнутое, скрытое (Cmd+H).

### 14.2. Local Network Access

Chrome 142+/147+ вводит LNA: соединения к локальным адресам требуют разрешения, а
service worker не может его запросить — только проверить выданное. Против гипотезы:
донорское расширение держит `ws://127.0.0.1:12377` на Brave 150 — loopback, самый
строгий случай. Проверка дешёвая и делается первой при подключении к удалённому
сервису.

## 15. Границы scope

Не входит: мобильные клиенты и чтение мобильных вкладок через `chrome.sessions`;
автоочистка **unruled**-вкладок внутри `main` (`main` — сток by design; дубли,
созданные самим куратором, при этом не допускаются механизмами §7); группы вкладок
Chrome; Peek / app-containment из Arc; автоматическое слияние окон (§9).

## 16. Фазы

1. **Вывод донорского `brave-window-mcp` из эксплуатации.** Первой, а не последней:
   у донора `execute_js` работает **без всякой галочки** (`<all_urls>` + `scripting`,
   options хранит только token/port/instanceId), а имена MCP-инструментов
   пересекаются с кураторскими (`execute_js`, `list_instances`). Пока оба
   зарегистрированы, «гейт на краю» — гейт одного из двух расширений в одном профиле,
   и обойти его можно, не заметив. Приёмка перечисляет профили поимённо.
2. Каркас сервиса: схема, миграции, слой доступа (§4), конфиг, Docker, `/healthz`.
3. Канал расширений: WSS, hello/эпоха/`conn_epoch`, ресинк со `snapshotSeq`,
   heartbeat, инжест событий (§5, §6).
4. Команды и архив: корреляция, `actions` с жизненным циклом, реконсиляция,
   restore + exemptions (§6, §7, §10).
5. Расширение: клиент сервиса, репортинг, тик, манифест (§5, §6).
6. Исполнение команд, включая `execute_js` под галочкой и `js_audit` (§6, §12).
7. Правила: модель, матчер, валидация, CRUD, серверное превью (§8).
8. Проход куратора: эвикция, дедуп, singleton, карантин, аренда (§7).
9. Стартпейдж: newtab, оффлайн-first, quick links, поиск, прыжок, статус-полоса (§10).
10. Редактор правил и архив с откатом прохода (§10).
11. MCP с разделением чтения и записи (§11).
12. Метрики и алерты (§12).
13. Деплой.
