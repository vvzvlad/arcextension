# Куратор вкладок — архитектура

Статус: **черновик, прошёл первый круг адверсариальной проверки**. Документ
итеративно улучшается; ишью заводятся только из сошедшейся версии.

История ревью здесь не ведётся — только сведённый результат.

---

## 1. Проблема и цель

Вкладки размножаются и смешиваются: инфраструктурные дашборды (Proxmox, Portainer,
Grafana) живут вперемешку с временными вкладками, дубли одного дашборда копятся
десятками, «что уже открыто» не видно.

Цель — реконструкция механик Arc (Spaces / Air Traffic Control / Auto Archive /
Library / Command Bar) поверх нескольких изолированных инстансов Brave: тематические
браузеры-«корзины», правила «адрес → домашний инстанс», отложенная сортировка по
бездействию, стартпейдж со списком всего открытого.

Ключевой принцип: **не мешать в моменте, сортировать постфактум.**

└──────────┬──────────────┘   └──────────┬─────────────┘    со своим --user-data-dir
           │ wss:// (исходящее)          │
           ▼                             ▼
┌───────────────── curator-service (Docker) ─────────────────────────────┐
│ WSS  /ext      — канал расширений                                       │
│ HTTP /api/*    — состояние, правила, превью, архив, focus, quick links   │
│ HTTP /mcp      — MCP streamable HTTP                                     │
│ HTTP /healthz  — liveness; /metrics — Prometheus                         │

│ Проход куратора раз в PASS_INTERVAL_MIN                                  │
└──────────────────────────────────────────────────────────────────────────┘
```

Адрес сервиса — конфигурация расширения (`serviceUrl`), а не константа дизайна.
Требование к нему одно: TLS-сертификат должен приниматься браузером без ручного
исключения, потому что расширение подключается из service worker'а, где ошибка
сертификата не даёт ни диалога, ни причины в JS — только `close` с кодом 1006.
Где публикуется сервис — вопрос деплоя, здесь не решается.

Стек — Python по каноническому гайду проекта: `src/` с pydantic-settings, вся
конфигурация из ENV, изменяемое состояние только в `data/`, тесты гейтят сборку.

**Донор** — `brave-window-mcp@f7f9c7c`: расширение берётся за основу (стр. 17),
Node-сервер не переиспользуется.

## 4. Модель данных

Канон схемы — этот раздел.

**Время.** Все метки в БД — epoch-миллисекунды **по часам сервиса**. Расширение
абсолютных клиентских временных меток не присылает вообще: вместо них — **возрасты**
(`ageMs`), которые сервис вычитает из своего `now`. Причина в §5.

`actions.kind ∈ {relocate, dedupe_close, singleton_close, window_merge, reset,
restore, cleanup}` — физическая операция. `actions.status ∈ {planned, opened, done,
failed, aborted, orphaned, deferred}` — жизненный цикл. `initiator` ортогонален
`kind`: MCP-инициированное переселение — `kind=relocate, initiator=mcp`.

`main_instance_id` живёт **только в ENV**, не в `settings`: две копии одного факта
без механической сверки — R3-нарушение.

### Слой доступа к БД

Из стр. 28 следуют обязательные требования:

- Все обращения к SQLite — вне event loop, через `asyncio.to_thread`, соединение с
  `check_same_thread=False`. **`aiosqlite` не подходит**: в нём каждый оператор —
  отдельный `await` к потоку соединения, поэтому любая многооператорная транзакция
  переживает `await` по построению и нарушает правило ниже. А таких транзакций дизайн
  требует минимум четыре: применение ресинка (§6), штамп ухода соседа по окну (§5),
  вставка строки `tabs` вместе с обновлением `actions` (§7.6), restore вместе с
  записью `exemptions` (§10). Транзакция целиком живёт внутри **одного** вызова
  `to_thread` — одна функция, ни одного `await` внутри.
- **Транзакция не должна переживать `await`.** Это и есть настоящее правило, а не
  «неявные транзакции запрещены»: прогон 2026-07-26 (Python 3.11.8) показал, что
  транзакция целиком внутри одного `to_thread` при отмене задачи доигрывается и
  коммитится, лок освобождается; а транзакция, растянутая через `await`, держит лок
  после отмены **одинаково и с `BEGIN IMMEDIATE`, и без него** — до `conn.close()`.
  Значит `BEGIN IMMEDIATE` от этой беды не спасает, и формулировка «неявность —
  причина» была неверной. Enforcement — `try/finally` с откатом.
- **`BEGIN IMMEDIATE` нужен по другой причине:** DEFERRED-транзакция, которая
  сначала читает, а потом пишет, проваливает апгрейд блокировки **без ретраев** —
  измеренный отказ на 0.000 с, `busy_timeout` при `SQLITE_BUSY_SNAPSHOT` не
  применяется вовсе.
- Один выделенный путь записи. С ним ошибка выше особенно дорога: зависший лок в
  singleton-писателе означает «до конца жизни соединения» = навсегда для всего
  сервиса.
- ⚠️ Замеры выше сделаны на macOS с SQLite 3.53.3 (Homebrew). Контейнер — Debian из
  `python:3.11-slim`, там libsqlite3 версии 3.4x. Перед реализацией прогнать те же
  пробы внутри образа и записать версию.
- `busy_timeout` задаётся явно, а не наследуется.
- WAL включается на старте.
- Бэкап — `VACUUM INTO`; он падает внутри открытой транзакции, поэтому корректность
  предыдущих пунктов — предусловие бэкапа. После каждой копии — `PRAGMA
  integrity_check` и sanity-запрос числа строк **до** ротации самой старой копии;
  успех экспортируется метрикой (§12).
- Миграции — раннер по `PRAGMA user_version`. **Каждый шаг — одна транзакция**,
  включающая и DDL, и присвоение `user_version` (в SQLite DDL транзакционен). Иначе
  шаг, упавший на середине, оставит версию старой, следующий старт переиграет его и
  упадёт на «duplicate column» уже навсегда — в crash-loop, ночью, без свидетелей.
  Перед первым шагом — `VACUUM INTO`-копия. Провал репортится метрикой, а не только
  падением процесса.

## 5. Время и критерий бездействия

### Эпоха сессии

`tab_id` осмыслен только внутри сессии браузера, а `instanceId` один и тот же между
запусками. Без эпохи команда может закрыть **не ту вкладку**, и архив запишет неправду.

- Расширение при старте генерирует uuid, хранит в `chrome.storage.session` (очищается
  при рестарте браузера, переживает смерть service worker), шлёт в `hello` и `resync`.
- Сервис проставляет `session_id` в каждую команду; расширение отвергает команду с
  чужим `session_id` кодом `stale_session`.
- Смена `session_id` ⇒ сервис удаляет все `tabs` инстанса и заводит заново с
  `opened_at = last_active_at = now`, `age_unknown=1`. Это реализует стр. 14 надёжно и
  независимо от того, переиспользует ли Chrome номера `tab_id`.

### Возрасты вместо меток

Расширение **не присылает абсолютных клиентских timestamp'ов**. В `resync` каждая
вкладка несёт `ageMs = Date.now() - tab.lastAccessed`; сервис пишет
`last_active_at = serverNow - ageMs`, но не больше `serverNow`.

Почему так: часы ноутбука могут уйти вперёд (севшая RTC, ручная правка, шаг NTP). При
работе с абсолютными метками и однократной калибровкой смещения в `hello` инстанс,
чьи часы обогнали серверные больше чем на `IDLE_MINUTES`, получает все вкладки
«бездействующими» — и ближайший проход выселяет его целиком. Монотонная дельта этим
не страдает и не требует выравнивания часов. Поле `clock_offset` в схеме отсутствует
намеренно.

### Часы вкладки

| Событие | `opened_at` | `last_active_at` |
|---|---|---|
| `tab_created` | `now` | `now` |
| `tab_activated {tabId, windowId}` | — | `now` — и **той же транзакцией** `now` для предыдущей активной вкладки этого окна |
| `window_focus_changed` (окно/приложение теряет фокус) | — | `now` для активной вкладки теряющего фокус окна |
| `tab_tick` | — | `now` |
| `tab_updated` со сменой **документа** (origin+path) | — | `now` (навигация = активность) |
| `tab_updated` со сменой только query/fragment | — | не трогается (см. ниже) |
| `open_tab` ack (создана куратором) | `src_opened_at` из `actions` | `src_last_active_at` из `actions` |
| `resync`, та же эпоха, известная пара, тот же url | сохраняется | `max(сохранённое, serverNow - ageMs)` |
| `resync`, другая эпоха / неизвестная пара | `now`, `age_unknown=1` | `now` |

Обе колонки — `NOT NULL`. Предикат бездействия:
`serverNow - last_active_at >= IDLE_MINUTES * 60000`.

**Событие `tab_deactivated` не вводится**: в Chrome API его нет, а `onActivated` не
несёт `previousTabId` (это Firefox), поэтому расширению пришлось бы вести собственную
карту «окно → активная вкладка» и терять её при каждой смерти service worker. Вместо
этого штамп «ухода» ставит **сервис** внутри обработчика `tab_activated` — он и так
обязан там сбросить `active=0` у соседей по окну, и это единственное место, где оба
факта наблюдаемы одновременно.

**Тик активной вкладки.** Расширение по `chrome.alarms` раз в `TICK_MS` шлёт
`tab_tick {tabId, windowId}` — **только** для вкладки `active=true` окна в фокусе,
и только если `chrome.idle.queryState()` возвращает `active`. Без тика «не трогал
час» означало бы «час не переключался на» (стр. 22): работаешь во вкладке два часа,
отводишь фокус — и через пять минут её увозит.

**Фокус не кэшируется, а запрашивается в момент тика** — `chrome.windows.getLastFocused()`
и проверка `.focused === true`. Хранение фокуса из событий оставляет ту же дыру, от
которой тик и защищает: по стр. 35 `onFocusChanged(WINDOW_ID_NONE)` приходит не
всегда, и залипшая вера в фокус означала бы вечный тик и вкладку, которая **не
стареет никогда**. Запрос в момент тика самоизлечивается на следующем же тике.

Проверка `chrome.idle.queryState(TICK_MS/1000)` (аргумент обязателен, минимум 15 с)
закрывает **только** случай «человек ушёл от машины» и заодно убирает следствие «окно
на переднем плане не стареет за ночь». Подменить ею проверку фокуса нельзя: `idle`
меряет ввод по **всей ОС**, а не по браузеру, поэтому при работе в другом приложении
она вернёт `active` — то есть в сценарии, ради которого её сюда добавляли, оба
условия истинны одновременно. Оконно-локального варианта в API нет.

**Почему не `lastAccessed`.** Стр. 22: он означает «стала активной» и не растёт, пока
во вкладке работают. Используется только как нижняя граница при ресинке.

### URL как идентичность и навигация как активность — это разные вещи

URL служит ключом идентичности в четырёх местах (`relocation_id`, `quarantine`,
`exemptions`, дедуп) и одновременно сигналом активности в пятом. Если не разделить
эти роли, страница, переписывающая собственный адрес, ломает все пять сразу и в одну
сторону. А переписывают его штатно и без участия человека: SPA складывает состояние
фильтров в адрес через `history.replaceState`, SSO прогоняет вкладку через
`/oauth2/...` при продлении сессии (с периодом, близким к самому порогу часа), и
`chrome.tabs.onUpdated` приходит на всё это.

Что было бы: `last_active_at` обновляется вечно ⇒ вкладка не переселяется никогда;
§9 требует бездействия **всех** вкладок окна ⇒ одна такая вкладка вечно блокирует
схлопывание своего окна; сменившийся url меняет `relocation_id` ⇒ детерминированная
идемпотентность не работает и в `main` появляется вторая копия; карантин снимается
«при смене url» ⇒ такая вкладка не карантинится в принципе; `exemptions` с ключом по
url испаряется при первой перезаписи ⇒ восстановленная через restore вкладка теряет
защиту и выселяется следующим же проходом.

Поэтому:

- **Активность** — только смена документа: сравниваются `origin + path`, изменения в
  query и fragment активностью не считаются.
- **Идентичность** во всех четырёх таблицах — нормализованный url (`origin + path`).
  Полный url хранится рядом, для архива и restore, где важен точный адрес.

### Активность и фокус

`active` в Chrome — свойство **окна**: последняя просмотренная вкладка тематического
браузера остаётся `active=1` навсегда. Поэтому «на экране прямо сейчас» — это
`tabs.active = 1 AND tabs.window_id = instances.focused_window_id`, а не один флаг
`active`. Хранить булев `focused` на инстанс недостаточно: при двух окнах он защищал
бы активные вкладки обоих.

`focused_window_id` — клиентский факт, который **переутверждается в каждом `resync`**;
`connected=0` тем же `UPDATE` обнуляет его в `NULL`. Иначе он залипает: ноутбук ушёл в
сон, событие потери фокуса не доставлено, и после возврата гард навсегда защищает
вкладку, которой на экране нет.

## 6. Протокол расширение ↔ сервис

Канон сообщений — этот раздел. Транспорт — WSS на `/ext`, JSON `{type, id?, …}`,
корреляция по `id`.

### Форма вкладки

`TabInfo = {tabId, windowId, url, title, favIconUrl, pinned, active, index, ageMs}`.
`ageMs` — см. §5. Тип окна приходит отдельным списком `windows` в `resync` и
событием `window_created`; вкладка, чьё окно сервису неизвестно, в проходе
пропускается.

### Установление связи

`hello {protocolVersion, token, instanceId, title, sessionId, allowExecuteJs}`
→ `hello_ack {ok, instanceId, connEpoch}`.

- `protocolVersion` — целое, сравнение точным равенством; несовпадение → отказ с
  записью `reject_reason='protocol'` и метрикой, а не тихая деградация.
- Неверный токен → `hello_ack {ok:false, error:{code:'auth'}}`, запись
  `reject_reason='auth'`, закрытие.
- Успех инкрементит `instances.conn_epoch`. **Все обработчики дисконнекта пишут
  условно**: `UPDATE instances SET connected=0, focused_window_id=NULL WHERE id=? AND
  conn_epoch=?`. Без этого добитый через полминуты полумёртвый старый сокет гасит
  живое новое соединение, и инстанс навсегда выпадает из курирования при исправной
  связи. События и ответы, пришедшие не с текущей эпохи, отбрасываются.
- Второй `hello` для занятого `instanceId` вытесняет старый сокет (закрытие +
  инкремент эпохи).
- После `hello_ack` сервис шлёт `resync_request {id}`.

### Готовность инстанса

`ready` — **вычисляемое условие**, а не хранимый флаг:

```
ready = connected = 1
    AND resync_at > pass_start
    AND session_id совпадает с последним hello
```

Хранимый флаг, который кто-то снимает, застревает: инстанс, потерявший `ready` из-за
одного таймаута, переставал бы получать `resync_request` (его шлют только `ready`) и
не мог бы восстановиться никогда. Поэтому `resync_request` рассылается **всем
`connected`**, а условие проверяется в момент использования.

### Ресинк

`resync {id, sessionId, snapshotSeq, focusedWindowId, tabs:[TabInfo], windows:[{id,type}]}`
— авторитетное полное состояние. Применение в одной транзакции: upsert всех
присланных вкладок, затем
`DELETE FROM tabs WHERE instance_id=? AND tab_id NOT IN (…) AND updated_at <= :snapshot_boundary`.

**`snapshot_boundary` = момент отправки того `resync_request`, чей `id` пришёл в
ответе**, по серверным часам. Сервис его знает, `resync` несёт `id`, и никакой
клиентской величины не требуется. Ответы с неизвестным или устаревшим `id`
игнорируются целиком. `resync_at` = та же величина: если брать момент **прихода**,
снимок, собранный до старта прохода, пройдёт проверку свежести, а строка, вставленная
из ack на `open_tab`, окажется «старше» границы и будет удалена — то есть защита,
ради которой условие и вводится, не сработает, а следующая вкладка с тем же URL
откроется вторым экземпляром в `main`.

Условие обязательно потому, что снимок `chrome.tabs.query` собирается асинхронно:
строка, вставленная сервисом из ack уже после начала сборки, физически не могла в
снимок попасть.

По той же причине расширение не отправляет события, возникшие во время сборки
снимка, раньше самого снимка.

### События (расширение → сервис)

`tab_created {tab}`, `tab_updated {tabId, url?, title?, pinned?, favIconUrl?}`
(отсутствующее поле = не менялось), `tab_activated {tabId, windowId}`,
`tab_tick {tabId, windowId}`, `tab_removed {tabId, isWindowClosing}`,
`tab_attached {tabId, windowId, index}`, `window_created {windowId, type}`,
`window_removed {windowId}`, `window_focus_changed {windowId|null}`.

Событие про вкладку, которой нет в зеркале, **игнорируется** с инкрементом метрики и
дебаунсированным `resync_request` этому инстансу — кроме `tab_created` и
`window_created`, которые объект как раз вводят. Заводить строку-заглушку по прочим
событиям нельзя: `opened_at` пришлось бы выставить в `now`, обнулив возраст вкладки.

**Собственные последствия куратора помечаются.** Расширение держит короткоживущее
множество `tabId`, затронутых его же `tabs.move` / `tabs.remove`, и помечает
порождённые ими события `cause:'curator'`. Сервис по таким событиям обновляет
`window_id` и `active`, но **не трогает `last_active_at`**.

Без этого куратор сам себе сбрасывает часы бездействия. Закрыли вкладку — Chrome
активирует соседа, приходит настоящий `tab_activated`, сосед получает `now` и на час
становится неприкосновенным; разбор тематического инстанса падает с «пачки за
проход» до **одной вкладки в час**, то есть сорок вкладок разбираются сорок часов.
Слияние окон (§9) переносит вкладки по одной, каждый перенос активной переводит
выделение на следующую — и всё слитое окно молодеет на час целиком. Наблюдаемо это
никак: система «работает, просто не спеша».

### Heartbeat и переподключение

Сервис шлёт `ping` каждые `HEARTBEAT_MS`, помечая соединение `alive=false`; `pong`
возвращает `true`; два пропуска подряд → отмена задачи соединения и `close`
(Starlette не даёт принудительного разрыва, стр. 30 — механизм именно такой; писатель
БД обязан быть cancel-safe, см. §4). Параметры `ws_ping_interval` / `ws_ping_timeout`
uvicorn задаются явно, иначе действуют неявные 20/20 с.

**Переподключение ведёт `chrome.alarms`**, а не таймер внутри service worker'а:
обработчик алярма (период ≥ 30 с — минимум MV3) безусловно обеспечивает открытый
сокет, независимо от состояния в памяти. Таймер «не пришёл `ping` за
`2.5 × HEARTBEAT_MS`» — только оптимизация поверх. Причина: по стр. 23 таймер
простоя MV3 сбрасывает лишь трафик по сокету, поэтому при мёртвом сокете service
worker умирает через 30 с и внутренний таймер не сработает никогда — тематический
инстанс не вернётся после ночного передеплоя вообще.

Счётчик backoff сбрасывается **только после `hello_ack {ok:true}}`** — у донора он
сбрасывается в обработчике `open` (стр. 19), а при неверном токене сокет успевает
открыться, и отказ авторизации молотит раз в секунду вечно.

### Команды (сервис → расширение)

`command {id, sessionId, connEpoch, command, params}` → `response {id, ok, result|error}`,
где `error = {code, message}`. Коды: `stale_session`, `precondition_failed`,
`no_such_tab`, `no_window`, `js_disabled`, `busy_dragging`, `internal`.

| Команда | Параметры | Результат |
|---|---|---|
| `open_tab` | `{relocation_id, url, pinned, active:false}` | `{tabId, already?}` |
| `close_tab` | `{tabId, expect:{url, activityRev}}` | `{ok}` / `precondition_failed` |
| `get_tab` | `{tabId}` | `{tab}` / `no_such_tab` |
| `focus_tab` | `{tabId}` | `{ok}` |
| `navigate_tab` | `{tabId, url}` | `{ok}` |
| `merge_windows` | `{}` | `{merged: n}` |
| `execute_js` | `{code, tabId?, world?}` | `{results}` / `js_disabled` |

**`expect` сверяет `url` и `activityRev`, но НЕ `active`.** Гардом «не трогать то,
что на экране» служит §7.2, и дублировать его в предусловии нельзя: по §5 последняя
просмотренная вкладка несфокусированного инстанса имеет `active=1` вечно, поэтому
предусловие `active:false` отказывало бы каждый проход — ровно для той вкладки, ради
которой строится система.

**`activityRev` — непрозрачный токен браузера, а не время.** Расширение ведёт на
каждую вкладку счётчик, инкрементируемый при каждом событии активности, которое оно
репортит, и отдаёт его в `TabInfo` и в событиях. Формат — `gen:rev`, где `gen` —
поколение, меняющееся при старте service worker'а: чужое поколение обязано
**отказывать**, то есть при потере карты система fail-closed в сторону «не закрывать».

Временем этот токен быть не может, и это не стилистика. `last_active_at` — величина
**серверных** часов, собранная из событий, которые штампует сервис (тик, активация,
штамп ухода соседа по окну). У расширения её нет и вывести её неоткуда:
`chrome.tabs.get().lastAccessed` — другие часы и другая семантика (стр. 22: не растёт,
пока во вкладке работают, и не двигается ни от тика, ни от потери фокуса), собственную
карту времён расширение вести не может по тому же аргументу, которым §5 отказался от
`tab_deactivated`, а абсолютных клиентских меток протокол не передаёт принципиально
(§4). Предусловие по времени реализатор смог бы выполнить единственным способом —
сравнив серверное зеркало с ним же, — и CAS выродился бы в сравнение переменной с
самой собой, то есть в отсутствие защиты. Токен обязан принадлежать той стороне,
которая наблюдает событие.

**`relocation_id` детерминирован и стабилен между проходами**:
`sha256(instance_from, session_id_src, tab_id, url, instance_to)`, он же — `UNIQUE` в
`actions`. Иначе идемпотентность не работает именно в том случае, ради которого
введена: потерянный ack даёт `failed`, следующий проход генерирует новый id, и в
цели появляется вторая копия — в `main`, где дедупа нет by design.

Расширение перед возвратом `already:true` **обязано подтвердить вкладку** через
`chrome.tabs.get` и пересоздать её, если она исчезла: иначе сервис получит
`{tabId, already:true}` на закрытую вкладку, вставит строку и закроет источник —
вкладка потеряна.

Карта `relocation_id → tabId` в `chrome.storage.session` чистится по
`chrome.tabs.onRemoved` и при терминальном статусе на стороне сервиса.

### Манифест расширения

- `permissions`: `tabs` (иначе `url`/`title`/`favIconUrl` отсутствуют, стр. 26, и
  правилам не с чем работать), `scripting`, `alarms`, `storage`, `idle` (тик, §5).
- `host_permissions`: **два паттерна, а не один** — `https://<host>/*` и отдельно
  `wss://<host>/*`. В match-patterns Chromium `ws`/`wss` — самостоятельные схемы, и
  https-паттерн запрос по `wss://` не покрывает; донор это подтверждает своим
  манифестом, где для локального моста выписан явный `ws://127.0.0.1/*`
  (`brave-window-mcp/extension/manifest.json:11`). Даёт ли `host_permissions`
  исключение из LNA — **не установлено** (стр. 34), но паттерн нужен независимо от
  этого. `<all_urls>` — только ради `execute_js`.
- `content_security_policy.extension_pages` — дефолт (`script-src 'self'`).
- `chrome_url_overrides.newtab` → страница стартпейджа.
- `options_page` — галочка `execute_js` живёт там (§12); без этого ключа страницы
  настроек нет, и гейт негде включить.
- `action` — бейдж состояния (§10).
- `key` — фиксирует ID расширения независимо от пути (стр. 21).

**Откуда берётся `instanceId`.** Свежий `--user-data-dir` стартует с пустым
`chrome.storage.local`, поэтому «id из настроек расширения» сам по себе не
появляется ниоткуда. Генератор инстансов (§13) кладёт рядом с расширением
`instance.json` с `{instanceId, title}`, расширение читает его через
`chrome.runtime.getURL` при первом старте и переносит в storage. Сервис **отвергает
`hello` с отсутствующим или дефолтным `instanceId`**: иначе два инстанса приходят с
одинаковым id, сталкиваются на `PRIMARY KEY (instance_id, tab_id)`, и авторитетный
`resync` каждого сносит вкладки другого — а правило «второй hello вытесняет старый
сокет» заставляет их чередоваться бесконечно.

### Внутренний интерфейс страница ↔ service worker

`runtime.sendMessage`: `get_identity` → `{instanceId, title}`;
`get_connection_state` → `{connected, lastSeenAt, rejectReason}`;
`enqueue_quicklink_op {op, url, title}`. Стартпейдж не хранит токен сам.

## 7. Проход куратора

Периодичность — `PASS_INTERVAL_MIN`. У прохода есть `pass_id`, он пишется во все
строки `actions` — это делает «откатить весь проход» одной операцией.

**Аренда с fencing.** `settings.pass_lease = {owner, epoch, until}`. Захват и
продление — одним CAS-запросом; продление каждые `LEASE_TTL_MS / 3`. **Каждая
запись прохода условна по `epoch`**: ноль изменённых строк ⇒ проход немедленно
прекращается. TTL без токена даёт только освобождение, но не взаимное исключение:
зомби-проход, переживший свой TTL, иначе продолжил бы слать команды параллельно с
новым — то есть механизм ломался бы ровно в том сценарии (rolling-редеплой), ради
которого введён.

### Пауза

**Кнопка «отключить всю автоматику на час»** (стр. 7а) — единственный аварийный стоп,
не разрушающий состояние. До неё варианты были такие: закрепить вкладку (частный
случай), остановить контейнер (убивает и стартпейдж, и архив) или удалить все правила
(отключает курирование по §8, но выбрасывает месяцы накопленной политики).

- Состояние — `settings.pause_until` (рантайм, не конфиг; `settings` по §4 именно для
  такого). Это **не** возвращение отвергнутого `CURATOR_MODE`: тот был ENV-флагом,
  требовал рестарта контейнера и жил вечно, а этот — кнопка с самоистечением.
- Проход проверяет паузу **первым делом**, до захвата аренды: ни проходового
  `resync_request`, ни команд, ни строк `actions`.
- **Включение паузы инкрементит `epoch` аренды.** Этого достаточно, чтобы остановить
  **уже идущий** проход: ближайшая же его условная запись изменит ноль строк, и он
  прекратится сам. Без этого кнопка проверялась бы только на входе, и человек,
  нажавший её посреди разбора двухсот вкладок, ещё несколько минут наблюдал бы, как
  «выключенная» система необратимо закрывает вкладки — отказ ровно того механизма,
  который здесь называется единственным аварийным стопом.
- **Пауза глушит всю автоматику, а не только проход.** Мутирующие глаголы `/api/*` и
  MCP при активной паузе отвечают `paused {until}`. Иначе кнопка не покрывает как раз
  тот класс инициаторов, который человек и подозревает, когда её жмёт: агент по MCP
  продолжал бы дёргать `relocate_tab` и `merge_windows` целый час. Исключение —
  собственные кнопки человека, и то с явным `force:true`, который пишется в `actions`
  как `initiator=user`.
- Дефолт — `PAUSE_DEFAULT_MIN` (60). Пауза всегда конечна: бессрочной не бывает,
  иначе однажды включённая она навсегда превращает систему в мёртвую. Продлевается
  повторным нажатием.
- Пауза **не** останавливает приём событий и ресинков (в том числе `resync_request`
  после `hello_ack` — запрет касается только проходового раунда): зеркало продолжает
  жить, иначе после снятия паузы первый проход работал бы по устаревшим данным.
- **Пауза не останавливает реконсиляцию** — см. ниже: та не принимает новых решений,
  а лишь доводит до конца или откатывает уже совершённые действия.
- **Снятие паузы сдвигает TTL-защиты.** Одним `UPDATE` все `quarantine.until` и
  `exemptions.until`, превышавшие момент начала паузы, сдвигаются на её длительность.
  Иначе часы идут, а проходов нет: исключение на 120 минут, выданное при restore,
  истекает внутри трёхчасовой паузы, ничего не защитив, и первый же проход после
  снятия делает ровно то, от чего человек защищался.
- **Снятие паузы немедленно запускает проход**, а не ждёт тика. Иначе каждое
  использование кнопки заканчивается ложным срабатыванием алерта «прохода не было
  дольше 3×`PASS_INTERVAL`» — к моменту истечения часовой паузы условие уже выполнено
  с запасом. Единственный алерт, отличающий мёртвого куратора от живого, научились бы
  игнорировать.
- **Видимость обязательна.** Забытая пауза неотличима от сломанного куратора, поэтому:
  строка в статус-полосе стартпейджа с обратным отсчётом (не бейдж, не всплывашка), в
  MCP `list_instances` — поле `paused_until`, метрика `curator_paused_until`. Алерт
  «прохода не было дольше 3×`PASS_INTERVAL`» подавляется на время паузы — иначе он
  зашумит и его отключат насовсем.

`POST /api/pause {minutes?}` включает, `DELETE /api/pause` снимает досрочно.

### Реконсиляция

**Отдельный шаг по таймеру, а не часть прохода**, и **пауза его не выключает**. Он не
принимает новых решений — только доводит до конца или откатывает уже совершённые
действия, и потому безопасен по определению. Если бы он жил внутри прохода, самая
опасная категория строк (`opened`/`orphaned` — те, у которых уже есть побочный эффект
в мире) обслуживалась бы единственным механизмом, который человек выключает именно
тогда, когда таких строк больше всего.

Строки в `planned` / `opened` / `orphaned` разбираются по существу: `get_tab` по
`target_tab_id`, и либо переселение доводится до конца, либо закрывается осиротевшая
копия (`kind=cleanup`). Слепая пометка `aborted` запрещена — она переклеивает ярлык
вместо компенсации, понижает завершившееся переселение до фантома, а осиротевшая
копия остаётся в `main` навсегда (дедупа там нет by design).

**CAS берётся из строки, а не из текущего зеркала.** `actions.src_activity_rev`
хранит ровно тот токен, из которого принималось решение; реконсиляция использует его
как `expect.activityRev`. Несовпадение означает не «довести», а компенсировать.
Иначе решение переживает собственное основание: строка `opened` пролежала час
(разрыв сети, пауза), человек этот час работал именно в этой вкладке, а реконсиляция
сравнила бы текущее значение с самим собой, сошлась и закрыла рабочую вкладку — гард
§7.2 к реконсиляции не применяется, она идёт до цикла.

После трёх неудачных попыток закрыть осиротевшую копию — `failed` и метрика
`curator_orphaned_total`: лишняя копия должна быть видима владельцу, а не притворяться
нормой.

Строки, доведённые реконсиляцией, **сохраняют исходный `pass_id`** — иначе откат того
прохода их не увидит.

Далее для каждой вкладки:

1. **Свежесть.** Проход начинается с `resync_request` каждому **`connected`**
   инстансу; в работу берётся инстанс, чей `resync_at > pass_start`. Не ответивший за
   `RESYNC_TIMEOUT_MS` из прохода исключается.
2. **Гарды.** Пропустить, если: url не http/https; `pinned=1`;
   `active=1 AND window_id = focused_window_id`; бездействие меньше `IDLE_MINUTES`;
   есть действующая запись в `exemptions`; есть действующая запись в `quarantine`.
3. **Куда.** Правило есть и инстанс ≠ домашний → домой; **это относится и к `main`**:
   `main` — источник для ruled-вкладок и не источник для unruled. Правила нет и
   инстанс тематический → в `main`. Правила нет и инстанс = `main` → не трогать.
4. **Цель не готова** → одна агрегированная строка `deferred` на проход (не строка на
   вкладку: 200 вкладок × проход раз в 5 минут = ~29 тысяч строк за ночь, и архив
   как страховка перестаёт быть читаемым).
5. **Дедуп и singleton — только с подтверждением от браузера.** Свежий `resync`
   источником подтверждения **не является**: он может быть старым на весь проход, а
   при гонке со снимком — ложно-свежим. Проверка — `get_tab` непосредственно перед
   закрытием источника; если для целевой вкладки успел прийти `tab_removed`,
   закрытие отменяется.

   **Дедуп по цели проверяется всегда, включая `main`.** Перед `open_tab` сервис
   ищет в цели вкладку с тем же нормализованным url; нашёл — вместо переселения
   `dedupe_close` источника (после подтверждения `get_tab` целевой). Иначе каждый
   проход добавлял бы в `main` по копии каждого бездомного дашборда, и §1 («дубли
   копятся десятками») воспроизводился бы самим куратором в том единственном
   инстансе, где их никто не разбирает.
6. **Переселение.** `open_tab {relocation_id}` → ack → строка `tabs` для новой
   вкладки вставляется **синхронно из ack** в той же транзакции, что и обновление
   `actions`, причём `opened_at`/`last_active_at` **переносятся из источника**
   (`src_opened_at`, `src_last_active_at`) → `close_tab {tabId, expect:{url,
   lastActiveAt}}`.
   - **Неоднозначный исход разрешается в сторону бо́льшего числа копий.** Дубль
     обратим, удаление нет, а стр. 16а санкционирует закрытие **дублей**, а не
     закрытие при неопределённости. Поэтому перед любой компенсацией сервис
     устанавливает факт запросом `get_tab` по источнику:
     - источника нет → закрытие уже произошло, переселение `done`;
     - источник есть и CAS сходится → повторить `close_tab` (детерминированный
       `relocation_id` и живая цель делают повтор безопасным);
     - источник есть и CAS не сходится → только тогда компенсировать: закрыть свою
       копию в цели, `status='aborted'` при успешной компенсации, иначе `orphaned`.

     Наивная трактовка «таймаут или `no_such_tab` = провал → закрыть копию» **теряет
     вкладку целиком**: обе эти ситуации чаще всего означают, что источник уже закрыт
     нами же — ответ не дошёл, потому что service worker умер сразу после
     `tabs.remove`, или сервис перезапустился между отправкой и ответом. Компенсация
     тогда уничтожает единственную оставшуюся копию, а архив пишет `failed`, то есть
     «ничего не произошло» — прямо противоположное правде.
   - `stale_session` компенсацией не является: инстанс сменил эпоху, его вкладки
     переучтены ресинком, строка уходит в `deferred`.
7. **Изоляция.** Каждая вкладка — в своём `try/except`; аренда снимается в `finally`.
8. **Карантин.** Три подряд неудачи по `(instance_id, url_normalized)` → `until = now
   + QUARANTINE_TTL_MIN`. Страйки копятся строкой с `until = 0`; гард §7.2 считает
   действующей записью только `until > now`. Максимум один страйк за проход; любой
   `done` по той же паре обнуляет счётчик. Ключ по URL, а не по `tab_id`: последний
   испаряется при рестарте браузера и от «отравленной строки» не защищал бы вовсе.

   **Страйк начисляется только за отказ, относящийся к самой вкладке** — то есть за
   `precondition_failed`, чей CAS разошёлся без участия куратора и без смены
   соединения. Всё, что вызвано соединением, сменой эпохи, слиянием окон или
   действиями самого куратора, даёт `deferred`. Готовность инстанса фиксируется на
   проход кортежем `(instance_id, conn_epoch, session_id, resync_at)`; его смена
   выводит инстанс из прохода **целиком**, а не роняет вкладки поштучно.

   Без этой оговорки страйк ставится за то, что к вкладке не относится: инстанс
   отвалился и вернулся внутри прохода (алярм реконнекта ≥ 30 с) — все команды
   остатка отвергаются по чужой эпохе, и пачка адресов уезжает в карантин на сутки.
   Или слияние окон подвинуло вкладку, CAS разошёлся, `aborted` — и так три утра
   подряд, после чего адрес выпадает **во всём инстансе**, включая все будущие
   вкладки с ним. `deferred` неудачей не считается и по-прежнему: иначе закрытый на
   обед `main` за три прохода отправил бы в карантин все вкладки всех инстансов.

   Карантин снимается по TTL, при смене `session_id` любой из сторон, при смене
   документа вкладки и вручную.

**Сходимость.** Дублирующиеся одинаковые URL внутри одного не-`main` инстанса
схлопываются автоматически (стр. 16а). Сравнение — точное по строке `tabs.url`:
нормализация (снятие фрагмента) закрывала бы реально разные страницы SPA, ради чего
и введён `singleton`.

Дедуп работает по инстансу, а не по окну: окна и так схлопываются автоматически
(§9), поэтому «два окна с одним URL» — состояние временное, и разделять эти два
механизма незачем.
Выживает вкладка с бо́льшим `last_active_at`, но **строки с `age_unknown=1`
проигрывают наблюдаемым при прочих равных**, а перенос часов из источника (п. 6)
не даёт свежесозданной копии выигрывать у оригинала: иначе недельная рабочая вкладка
со скроллом и открытыми панелями систематически уничтожалась бы в пользу пустой
свежезагруженной.

**Ограничителя числа действий нет** (стр. 15). Защита от испорченного правила —
превью при сохранении (§8), `run_pass {dry_run:true}` и архив с откатом прохода.

`dry_run` берёт аренду, шлёт `resync_request`, `actions` не пишет, счётчики попыток и
карантина не трогает, возвращает план в ответе.

## 8. Правила

Канон семантики матчера — этот раздел, единственный. **Реализация каноническая —
серверная (Python)**; браузер матчер не дублирует.

- Правило: `pattern → instance_id` + флаги `singleton`, `canonical_url`, `note`.
- Схемы кроме http/https не матчатся никогда.
- Разбор: `urlsplit`, затем явная нормализация — `hostname` в нижний регистр, IDN →
  punycode (`idna`), снятие завершающей точки FQDN, IPv6-литерал приводится к форме
  без скобок. Отсутствующий порт = порт по умолчанию схемы (80 / 443).
- `pattern` = `<hostPattern>` или `<hostPattern>:<port>`; порт отсутствует → любой.
- `hostPattern` сравнивается с `hostname` целиком (anchored), `*` → `.*`, остальное
  экранируется. Частичного совпадения нет: `borneo.lc` не матчит ни `evil-borneo.lc`,
  ни `x.borneo.lc`.
- Специфичность: (а) явный порт специфичнее его отсутствия; (б) больше символов в
  `hostPattern` без учёта `*`; (в) меньший `rules.id`.
- **Валидация при сохранении**, а не исключение во время прохода: паттерн, который
  не разбирается (например, введённый как полный URL `https://borneo.lc/path`),
  отвергается с человекочитаемой ошибкой. Уже сохранённое правило, которое перестало
  компилироваться, помечается `invalid=1`, в матчинге не участвует, считается в
  метрике и подсвечивается в редакторе — но **никогда не роняет проход**.
- **Пустая таблица правил отключает ветку «unruled → main» целиком.** Пустая политика
  означает «ничего не делать», а не «переселить всё».

`singleton=1` — «приложение» (прокс, Portainer, Grafana): в домашнем инстансе
максимум одна вкладка на правило. Точный URL-дедуп таких не ловит: SPA-фрагменты
делают адреса формально разными.

**Превью — серверное** (`POST /api/rules/preview`), а не браузерное: иначе оно
считалось бы другой реализацией матчера и систематически врало бы на IDN и IPv6 — а
превью по стр. 15 единственная защита вместо снятого ограничителя.

**Превью моделирует весь следующий проход, а не только сохраняемое правило.**
Причина: по правилу выше пустая таблица отключает ветку «unruled → main» целиком,
поэтому переход от нуля правил к одному включает сток для **всех** тематических
инстансов — эффект, который не является свойством сохраняемого правила и который
пер-правиловое превью выразить не может. А это ровно самый крупный залп, который
система когда-либо произведёт. Переход «пусто → не пусто» требует отдельного
подтверждения.

Превью возвращает **раздельно** число переселений и число закрытий со списком
примеров URL; необратима именно вторая цифра. При `closures > 0` сохранение требует
эхо-подтверждения `confirm_impact`.

`canonical_url` применяется **только** ручным действием `reset` (§10, §11); проход
содержимое вкладок не меняет.

**Нативно закреплённые вкладки (`pinned=1`) не переселяются и не закрываются.** Это
моё дизайн-решение, не решение владельца: он убрал пин как *механизм маршрутизации*
(стр. 5), здесь пин используется как сигнал «руками не трогать». Убирается одной
строкой в §7.2.

## 9. Окна

Окна инстанса схлопываются в одно **автоматически** (стр. 7).

**Гард — то же бездействие, что и везде**: сливается только обычное окно, все вкладки
которого бездействуют дольше `IDLE_MINUTES`, и никогда — окно, содержащее вкладку на
экране. Именно эта задержка снимает риск сценария «вытащил дашборд во второе окно
смотреть два графика рядом»: пока с окном работают, оно не трогается, а через час
после того, как его бросили, схлопывание уже безобидно. Мгновенное слияние (что я
предлагал раньше как аргумент против автоматики вообще) действительно было бы
причиной выключить систему; отложенное — нет.

**Закреплённые вкладки слияние не двигает вовсе.** Перенос сбрасывает `pinned`, а
между `tabs.move` и восстановлением флага расширение может потерять ход: MV3 убивает
service worker на длинном цикле, человек берётся за вкладку мышью, браузер закрывают.
Тогда в сервис приходит `tab_updated {pinned:false}` — и §7.2 больше не защищает
вкладку, то есть косметическая операция уничтожает единственный доступный человеку
щит «руками не трогать», а следующий проход её переселяет или закрывает необратимо.
Поэтому переносятся только незакреплённые; окно, в котором остались закреплённые,
просто не исчезает. Это видимый и безопасный компромисс вместо компенсации
несуществующим откатом.

**Решение принимает сервис, команда его переносит.** Бездействие вычислимо только на
сервере, поэтому сигнатура — `merge_windows {windowIds[], targetWindowId}`; пустой
объект оставлен для ручной кнопки «слить всё сейчас». Если бы расширение получало
`{}` и решало само, оно схлопнуло бы и то окно, в котором человек прямо сейчас
смотрит два графика — ровно тот сценарий, ради которого введена часовая задержка.

Целевое окно — обычное окно с наибольшим числом вкладок; при равенстве — меньший
`window_id`. Окна типа popup/devtools/app не сливаются и в подсчёте не участвуют.
Отказ `busy_dragging` (человек держит вкладку мышью) провалом не считается и
повторяется на следующем проходе.

**Слияние — шаг 9 прохода, после цикла по вкладкам** (§7). Иначе решения по вкладкам
принимались бы по картине окон, которая меняется под ними: `open_tab` выбрал бы окно,
исчезающее через секунду, а `focused_window_id` указывал бы на несуществующее.
Результат — строка `actions(kind='window_merge')` со списком перенесённых `tab_id`;
откату не подлежит (исходной раскладки окон в схеме нет и хранить её незачем).

Кнопка «слить окна сейчас» на стартпейдже и MCP-инструмент остаются — для случая,
когда ждать час не хочется.

`open_tab` выбирает окно детерминированно (то же «обычное окно с наибольшим числом
вкладок»), а не полагается на последнее сфокусированное, которым может оказаться
popup. Если обычных окон нет — на macOS браузер живёт с нулём окон ежедневно —
`chrome.windows.create` с `focused:false, state:'normal'`: фоновое окно не прерывает
работу, а отказ уводил бы инстанс в `deferred` и далее в карантин.

## 10. Стартпейдж и HTTP API

Newtab-страница расширения (стр. 25). Сборка — Vue 3 + Vite в папку расширения.

**Оффлайн-first (стр. 9).** Первая отрисовка не ждёт сети: свои вкладки —
`chrome.tabs.query`; чужие инстансы и quick links — кэш в `chrome.storage.local`
(ровно объект `StateResponse` плюс `cached_at`); затем фоновый `GET /api/state`
обновляет данные и кэш. Формулировка «синхронно» некорректна — в MV3 оба API
асинхронны; корректно: «первая отрисовка только из локальных источников».

Все ассеты локальны. В оффлайне свои вкладки и quick links полностью рабочие; чужие
группы помечены «кэш от &lt;время&gt;»; прыжок на чужую вкладку неактивен. Пустого newtab
не бывает, в том числе на свежем профиле без кэша.

**Три способа получить молча пустой стартпейдж.** Все проверены прогоном
2026-07-26 (vite 6.4.3 / vue 3.5.40, страница открыта в Brave 150 под дефолтным
`script-src 'self'`); у каждого своя проверка, одной на всех не существует:

1. **Импорт рантайм-компилятора** (`vue/dist/vue.esm-bundler.js`) тянет
   `new Function` → блокируется CSP. Ловится грепом по сборке:
   `grep -rE "new Function|eval\(" dist/`. **Экранирование скобки обязательно**:
   `grep 'new Function|eval('` — это BRE, где `|` литерал, и против файла, буквально
   содержащего `new Function`, он возвращает «не найдено»; с `-E` та же строка
   падает на несбалансированной скобке. Неверно записанный guard вечно зелёный.
2. **Строковый `template:`** при runtime-only импорте `new Function` **не даёт**
   (в сборке ноль вхождений) — страница просто рендерит пустоту, без ошибок в
   консоли. Грепом и проверкой CSP не ловится вообще.
3. **Дефолтный `base: '/'`** у Vite: пути вида `/assets/index-<hash>.js` внутри
   `chrome-extension://<id>/` резолвятся в корень расширения и дают 404 — пустая
   страница, ноль исключений. Требование `base: './'` — часть конфига, проверяется
   `grep -q 'src="\./assets' dist/index.html`.

Единственная проверка, покрывающая все три, — **smoke-тест рендера после сборки**:
загрузить собранную страницу и убедиться, что корневой узел непустой. Он и есть
критерий приёмки; грепы — быстрая подстраховка.

Dev-сервер Vite для страницы расширения непригоден; цикл — пересборка.

**Пауза показывается в статус-полосе строкой с обратным отсчётом** и кнопкой снять
досрочно (§7). Не бейджем и не всплывашкой: забытая пауза выглядит точно как
сломанный куратор, и увидеть её надо там же, где смотрят «почему ничего не
происходит».

**Статус-полоса различает четыре состояния инстанса**, а не два: никогда не видели /
видели N назад (закрыт) / подключён, но зеркало не свежее / отвергнут с причиной и
временем. Иначе отказ авторизации, несовпадение версии протокола, умершая от CSP
страница, блокировка LNA и «браузер просто закрыт» выглядят одинаково — серым
инстансом. Бейдж `chrome.action.setBadgeText` показывается внутри отказавшего
браузера, то есть там, куда владелец и не заходит; полагаться на него нельзя.

**Прыжок.** Своя вкладка — `chrome.tabs.update` + `chrome.windows.update`. Чужая —
`POST /api/focus`. Поднимет ли macOS чужое приложение — не доказано (стр. 33),
поэтому до результата спайка §14.1 UI показывает «активировано в &lt;инстанс&gt;» и подъёма
не обещает.

**Quick links.** Очередь оффлайн-операций живёт в `chrome.storage.local` (оффлайн
может длиться днями, `storage.session` умрёт с браузером), принадлежит service
worker'у, сливается `POST /api/quick_links/ops` с `Idempotency-Key`. Разрешение
конфликтов — last-write-wins по времени приёма на сервере; `position` пересчитывает
сервер (append в конец), явная операция `reorder` для перестановки.

### Эндпоинты

| Метод | Путь | Тело / ответ |
|---|---|---|
| GET | `/api/state` | `StateResponse` |
| POST | `/api/focus` | `{instance, tabId}` → `{ok}` |
| GET/POST/PUT/DELETE | `/api/rules[/:id]` | CRUD; POST/PUT требуют `confirm_impact` при `closures>0` |
| POST | `/api/rules/preview` | `{pattern, instance_id, singleton}` → `{relocations, closures, examples[]}` |
| POST | `/api/rules/:id/reset` | → `{ok}` (ручной `reset`, §8) |
| GET | `/api/actions` | `{items[], total}`; фильтры по `kind`, `pass_id` |
| POST | `/api/actions/:id/restore` | → `{ok}` |
| POST | `/api/passes/:pass_id/undo` | откат прохода целиком |
| POST | `/api/run_pass` | `{dry_run?}` → план или `{started}` |
| GET/POST/DELETE | `/api/exemptions` | «не трогать до …» |
| POST | `/api/quick_links/ops` | массив операций |
| POST | `/api/instances/:id/merge_windows` | → `{merged}` (немедленно, §9) |
| POST/DELETE | `/api/pause` | `{minutes?}` → `{paused_until}` / снять досрочно |

StateResponse = {
  server_now, last_pass_at, last_pass_ok, rules_total, rules_invalid,
  instances: [{id, title, connected, resync_at, last_seen_at,
               reject_reason, reject_at, focused_window_id}],
  tabs:      [{instance_id, tab_id, window_id, url, title, fav_icon_url,
               pinned, active, last_active_at, age_unknown}],
  quick_links: [{id, url, title, position}]
}
```

Свои вкладки клиент отфильтровывает сам (они уже есть из `chrome.tabs.query`).

**`restore`.** Открывает URL в `instance_from`, если тот готов, иначе отказ с явной
ошибкой (молчаливая подстановка `main` кладёт вкладку не туда). В одной транзакции с
открытием пишется `exemptions` с `until = now + RESTORE_EXEMPTION_MIN`, иначе
следующий проход выселит восстановленную вкладку снова — и так по кругу, пока она не
уйдёт в карантин, то есть «restore ломает вкладку». Перед открытием — дедуп по URL.
Пишется одна строка `actions(kind='restore', initiator='user')`, в исходной строке
проставляется `restored_at`.

## 11. MCP

`POST /mcp`, streamable HTTP (стр. 13). Auth — `Authorization: Bearer <MCP_TOKEN>`.

**Монтирование (стр. 27).** `mcp.run(transport="streamable-http")` поднимает
собственный uvicorn и забирает порт — непригодно, сервису нужны ещё `/ext`,
`/api/*`, `/healthz`, `/metrics` на том же порту.

Наивный `app.mount("/mcp", mcp.streamable_http_app())` ломается по **двум
независимым причинам**, и обе надо снять:

1. **Lifespan вложенного приложения не пробрасывается.** Starlette выполняет
   lifespan только у корневого приложения, поэтому task group session manager'а
   никогда не создаётся → `RuntimeError: Task group is not initialized`. Лечится
   входом в `mcp.session_manager.run()` в lifespan **хост-приложения**;
   `stateless_http=True` тут не помогает — проверка на неинициализированную группу
   стоит раньше ветвления.
2. **`streamable_http_app()` уже регистрирует `/mcp` внутри себя**, поэтому
   монтирование его же под `/mcp` удваивает путь.

Достаточно снять обе — тогда работает и `Mount`, и точный `Route`. Причина «Mount
даёт 307, а клиенты не следуют редиректам», которую я записал раньше, **ложна**: SDK
хардкодит `follow_redirects: True`, и реальный `streamablehttp_client` проходит
handshake через 307. Версию SDK по этой причине пинить не нужно.

⚠️ **Порядок вызовов обязателен:** `streamable_http_app()` вызывается **один раз до**
входа в lifespan. `session_manager` создаётся лениво и до этого вызова бросает
`RuntimeError: Session manager can only be accessed after calling
streamable_http_app()`. Наивная реализация рецепта — `async with
mcp.session_manager.run():` в lifespan плюс собственный `Route` — падает на старте
контейнера ещё до первого запроса. Возвращённое приложение при этом можно не
монтировать: достаточно взять из него хендлер.

**Пауза** — `pause {minutes?}` и `resume`; состояние отдаётся в `list_instances`
полем `paused_until` (§7), чтобы агент не принял паузу за поломку.

**Чтение и запись разделены.** Инструменты чтения — всегда: `list_instances`,
`list_tabs`, `get_rules`, `list_actions`, `run_pass {dry_run:true}`. Инструменты
записи (`upsert_rule`, `delete_rule`, `open_tab`, `close_tab`, `focus_tab`,
`relocate_tab`, `reset_singleton`, `merge_windows`, `execute_js`, `run_pass` без
`dry_run`) доступны только при `MCP_WRITE_ENABLED=true`.

`upsert_rule` подчиняется тому же правилу подтверждения, что и HTTP: возвращает
impact и требует эхо `confirm_impact`. Иначе из трёх заявленных защит (§7) на пути
MCP не работала бы ни одна: превью живёт в UI и не вызывается, `dry_run`
опционален, архив — постфактум.

## 12. Отказы, наблюдаемость, безопасность

### Наблюдаемость

- **`/metrics`**, Prometheus, Bearer по отдельному `METRICS_TOKEN` — read-only.
  Отдельный токен обязателен: у владельца scrape-креденшл лежит открытым текстом в
  git (стр. 32), и если это окажется `EXT_TOKEN` или `API_TOKEN`, в историю навсегда
  уедет ключ от правил, `run_pass`, `restore` и списка всех URL.
- Метрики: `curator_last_pass_ts`, `curator_last_pass_ok`,
  `curator_actions_last_pass{kind}`, `curator_instance_connected{id}`,
  `curator_instance_last_seen_ts{id}`, `curator_auth_rejections_total`,
  `curator_deferred_total{to_instance}`, `curator_quarantined_total`,
  `curator_paused_until`, `curator_rules_total`, `curator_rules_invalid`,
  `curator_backup_last_ok_ts`,
  `curator_backup_bytes`, `curator_migration_failed`.
- **Алерты — часть этого дизайна, а не «метрики есть».** В конфиге владельца ровно
  одно правило с `noDataState: Alerting`, и оно привязано к gitmost (стр. 31);
  правило, скопированное в домашнем стиле, при исчезновении данных уйдёт в `OK`,
  то есть замолчит ровно при аварии. Минимум: `up{job="curator"}` и
  `time() - curator_last_pass_ts > 3 * PASS_INTERVAL`, оба с `noDataState: Alerting`,
  плюс правило на `curator_last_pass_ok` и на возраст бэкапа > 36 ч.
  `curator_instance_connected` алертабельной не является — ноутбук спит каждую ночь.
- **`/healthz` — только liveness.** Ошибки курирования в него не складываются:
  оркестратор перестаёт направлять трафик в нездоровый контейнер, и «проход сломался»
  превратилось бы в «все расширения отвалились».

### Отказы

- Backoff сбрасывается только после успешного `hello_ack` (§6).
- `main_instance_id`, который ни разу не подключался → ветка стока выключена,
  метрика и баннер.
- `rules.instance_id` валидируется против `instances` при записи: опечатка в имени
  инстанса иначе даёт вечный невидимый `deferred`, а превью её не покажет — оно
  считает совпадения паттерна, а не существование цели.
- Ретеншн `actions` — `ACTIONS_RETENTION_DAYS`; окно восстановления документируется
  как заведомо меньшее. `js_audit` — свой, длинный ретеншн.
- Бэкап — ночной `VACUUM INTO` с `integrity_check` и метрикой успеха; путь копий
  монтируется отдельно от тома БД.

### Безопасность

- **`API_TOKEN` отдельно от `EXT_TOKEN`.** Один общий токен означал бы: утечка из
  одного одноразового тематического браузера (а он лежит открытым текстом в
  `chrome.storage.local` каждого профиля) даёт и весь `/api/*`, и право
  представиться любым `instanceId` по WS — включая `main`, чей `resync` делает
  `DELETE`.
- **CORS — только явные `chrome-extension://`-origin'ы**, никогда `*`. Заголовок
  `Authorization` вынуждает preflight, что дополнительно отсекает случайные страницы.
- Требование к развёртыванию: сервис не должен быть доступен из публичной сети.
- Все токены обязательны, пустой = отказ старта.
- `execute_js` — галочка в options каждого расширения, дефолт выкл, enforcement на
  краю (стр. 12). Инстанс сообщает состояние галочки в `hello`. Каждый вызов пишется
  в `js_audit` **до отправки** (чтобы отказы тоже попадали): полный код, `world`,
  `tabId` и URL на момент выполнения, исход. Усечённый код нереконструируем, а общий
  ретеншн с рутинными `dedupe_close` уничтожал бы единственный след выполнения
  произвольного кода вместе с шумом.

## 13. Инстансы

Инстанс — отдельный `.app`, запускающий системный Brave со своим `--user-data-dir`
(стр. 4). Генератор создаёт бандл с уникальным `CFBundleIdentifier`, иконкой и
лаунчером.

Отдельная идентичность приложения (своя иконка и имя в Dock, а не «Brave Browser»)
**наблюдалась** на прототипе `infra-browser` 2026-07-26: после перезапуска бандл
показывался своей иконкой. Наблюдение однократное и не разобрано по механизму —
лаунчер `exec`ает системный бинарь Brave, и априори ожидалось обратное. Если на
практике идентичность окажется неустойчивой, альтернатива — полная копия
`Brave Browser.app` на инстанс, и это заметно меняет цену этой фазы (~400 МБ и
отдельное обновление на каждый инстанс).

⚠️ **Каталог расширения — по копии на инстанс**, потому что `instance.json` лежит
внутри него и обязан различаться. Следствие, которое надо держать в голове: код
расширения размножен, а `protocolVersion` сравнивается точным равенством (§6) —
пропущенная при обновлении копия отвергается на `hello` навсегда, и видно это только
в статус-полосе. Генератору нужна явная операция «перештамповать все инстансы»,
обновляющая заодно код. Альтернатива — вынести id из бандла (например, в
`--user-data-dir`), тогда каталог остаётся один.

Генератор также кладёт рядом с расширением `instance.json` с `{instanceId, title}` —
единственный способ, которым id попадает в свежий профиль (§6).

Расширение ставится флагом `--load-extension` (стр. 20). Оговорки: не сработает при
включённом Enhanced Safe Browsing и при политике `ExtensionInstallTypeBlocklist`.

Запасной путь — CDP `Extensions.loadUnpacked`. ⚠️ **Условия его применения не
установлены**: один источник утверждает, что с M149 спецфлаги не нужны, другой — что
домен остаётся Experimental и требует `--enable-unsafe-extension-debugging` вместе с
`--remote-debugging-pipe` (а через `--remote-debugging-port` возвращает «Method not
available»). Своим прогоном я это не проверял. Пока не проверено — запасным путём
считать нельзя; проверка стоит десять минут и делается **до** того, как запасной путь
понадобится, а не в момент поломки.

**Риск:** иммунитет Brave держится на том, что проверка в апстриме сидит внутри
`#if BUILDFLAG(GOOGLE_CHROME_BRANDING)`. Если Chromium вынесет её наружу, Brave
унаследует запрет на ближайшем ребейзе без сигнала — поэтому запасной путь описан
заранее.

## 14. Открытые спайки

### 14.1. Кросс-инстансный фокус окна на macOS

Поднимает ли `chrome.windows.update(id, {focused:true})` в инстансе B приложение B
поверх A. Дизайн корректен при обоих исходах: при отрицательном UI не обещает
подъёма. Проверить для трёх состояний окна B: обычное, свёрнутое, скрытое (Cmd+H).

### 14.2. Local Network Access — ОТКРЫТ (первая попытка была невалидной)

Первый прогон целился в `10.20.30.3` — собственный WG-адрес той же машины, поэтому
не проверил ничего: пакет не покидал хост. Спайк требует **трёх** прогонов, и это
первое, что делается вообще, потому что от него зависит весь транспорт:

1. **Удалённый RFC1918-хост через WireGuard** — не адрес самого ноутбука. Цель за
   туннелем, сервер на удалённой стороне.
2. **По `wss://` с реальным сертификатом**, а не по plain `ws://`: отказ по
   сертификату из service worker'а неотличим от отказа по LNA — и то и другое
   `close 1006` без причины (§3).
3. **Отрицательный контроль без `host_permissions`** на цель. Без него утверждение
   «исключение даёт `host_permissions`» остаётся догадкой: два положительных случая
   причинности не устанавливают.

Аварийный выход, если исключение не действует: политика
`LocalNetworkAccessAllowedForUrls`.

## 15. Границы scope

Не входит: мобильные клиенты и чтение мобильных вкладок через `chrome.sessions`;
схлопывание дублей, созданных **пользователем** внутри `main` (`main` — сток by
design; дубли, которые создал бы сам куратор, не допускаются проверкой цели в §7.5);
группы вкладок Chrome; Peek / app-containment из Arc.

## 16. Фазы

1. **Вывод донорского `brave-window-mcp` из эксплуатации.** Первой, а не последней:
   у донора `execute_js` работает **без всякой галочки** (`<all_urls>` + `scripting`,
   options хранит только token/port/instanceId), а имена MCP-инструментов
   пересекаются с кураторскими (`execute_js`, `list_instances`). Пока оба
   зарегистрированы, «гейт на краю» — гейт одного из двух расширений в одном профиле,
   и обойти его можно, не заметив. Приёмка перечисляет профили поимённо.
2. Каркас сервиса: схема, миграции, слой доступа (§4), конфиг, Docker, `/healthz`.
3. Канал расширений: WSS, hello/эпоха/`conn_epoch`, ресинк со `snapshotSeq`,
   heartbeat, инжест событий (§5, §6).
4. Команды и архив: корреляция, `actions` с жизненным циклом, реконсиляция,
   restore + exemptions (§6, §7, §10).
5. Расширение: клиент сервиса, репортинг, тик, манифест (§5, §6).
6. Исполнение команд, включая `execute_js` под галочкой и `js_audit` (§6, §12).
7. Правила: модель, матчер, валидация, CRUD, серверное превью (§8).
8. Проход куратора: эвикция, дедуп, singleton, карантин, аренда (§7).
9. Стартпейдж: newtab, оффлайн-first, quick links, поиск, прыжок, статус-полоса (§10).
10. Редактор правил и архив с откатом прохода (§10).
11. MCP с разделением чтения и записи (§11).
12. Метрики и алерты (§12).
13. Деплой.
14. Генератор инстансов (§13).
15. Автослияние окон: серверный шаг прохода + команда `merge_windows` (§9).
16. Пауза: хранение, гейт на пути записи, кнопка, сдвиг TTL при снятии (§7).
